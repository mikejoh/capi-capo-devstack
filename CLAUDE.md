# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository purpose

This is a **tutorial repository**, not a software project. It has no build, lint, or test commands, no CI, and no source code. The `README.md` is an 11-step walkthrough for running Cluster API (CAPI) + Cluster API Provider OpenStack (CAPO) locally on top of a DevStack KVM install, using minikube as the management cluster and [Talos Linux](https://www.talos.dev/) (via CABPT/CACPPT) as the workload cluster's node OS instead of kubeadm/Ubuntu. Every OpenStack credential the tutorial uses is minted on demand by OpenBao and delivered via External Secrets Operator — no static, non-expiring per-cluster password anywhere. The repo exists to hold sample config files referenced by the README and `docs/`; treat those as the source of truth.

The kubeadm/Ubuntu path (static `clouds.yaml`, `image-builder`, Flannel→Cilium via ArgoCD) that used to be the main walkthrough has been removed in favor of Talos. `argocd/` (Flannel bootstrap, Cilium via ArgoCD, the CNI-migration Job) and OCCM wiring still exist in the repo but are currently **not referenced by the README** — they were never adapted/verified for the Talos path (different pod CIDR, no Talos kube-proxy-disable config patch). Treat them as parked, not as part of the current walkthrough.

## What lives here

- `README.md` — the walkthrough. Numbered steps 1–11.
- `clouds.yaml.example` — blank template for the `openstack` client auth config, for readers who'd rather run the one-off admin `openstack` CLI commands (project/user creation, image upload) from their workstation instead of SSHing into the DevStack VM. Not required by any step — the tutorial's actual cluster credential comes from OpenBao, not this file.
- `.gitignore` — keeps the real `clouds.yaml` and any `*.kubeconfig`/`*.talosconfig` out of git.
- `LICENSE` — Apache 2.0.
- `openbao/` — PoC of the "secret0" problem: no static, non-expiring per-cluster OpenStack user/password. `00`-`03` deploy a single-node OpenBao (file storage, `disable_mlock`, PoC-grade — data lost on pod restart) running `vault-plugin-secrets-openstack` (v0.2.0 binary fetched by an initContainer), plus a dedicated `openbao` ServiceAccount bound to `system:auth-delegator` so OpenBao can run its own `kubernetes` auth method (validates other pods' SA tokens via TokenReview against the same minikube API server). `04-rbac.yaml` also creates the shared `cluster-bootstrapper` ServiceAccount used by every per-cluster roleset-creation Job. `setup.sh` is the one-shot init script — re-run it in full any time the pod restarts (emptyDir storage does not survive that); it inits/unseals, registers the plugin, configures `openstack/config/auth` with one narrowly-scoped root OpenStack credential (a dedicated project + user, created by hand for this PoC — see `docs/dynamic-openstack-credentials.md`), creates the `capo-poc-member` roleset, enables `auth/kubernetes` with an `eso` role (glob policy `openstack/creds/*`, read-only — shared across every cluster) and a `cluster-bootstrapper` role (policy scoped to `openstack/roleset/*` `create`/`update` only, no read).
- `capo-poc/` — the consumer side, and an *optional* sanity check (README step 7 / `docs/dynamic-openstack-credentials.md` step 4). `01-external-secret.yaml` is a `VaultDynamicSecret` generator (ESO authenticates to OpenBao via its own ServiceAccount token, no static token — `auth.kubernetes` with no `secretRef`/`serviceAccountRef` falls back to the controller's bound token) feeding an `ExternalSecret` that templates the minted `application_credential_id`/`secret` into a `clouds.yaml` `Secret`. `02-cluster-identity.yaml` is an `OpenStackClusterIdentity` pointing at that Secret. `03-openstackcluster.yaml` is a deliberately minimal `OpenStackCluster`/`Cluster` pair — no `MachineDeployment`/control plane — used to prove `capo-controller` can reconcile real Neutron resources using a credential that's seconds old, without needing a bootable node image. Superseded by `talos-devstack01/` for anyone going all the way to a real cluster.
- `talos-devstack01/` — the tutorial's actual payoff cluster (README step 9): same OpenBao/ESO credential chain as `capo-poc/` (own namespace, own roleset `talos-devstack01-member`, own `OpenStackClusterIdentity`), but `04-cluster.yaml` is a full `Cluster`+`TalosControlPlane`+`MachineDeployment`+2×`OpenStackMachineTemplate` (1 CP + 1 worker) using CABPT/CACPPT (`TalosControlPlane`/`TalosConfigTemplate`, `generateType: controlplane`/`worker` — bare-minimum form, no hand-written Talos machine config) instead of kubeadm kinds. No `sshKeyName` anywhere: Talos has no SSH server. Pod CIDR is `10.8.0.0/16` — deliberately *not* aligned with `argocd/flannel.yaml`/`argocd/cilium-values.yaml` (`192.168.0.0/16`), since this cluster isn't wired into that path. `apiServerLoadBalancer.enabled: true` — see the OpenBao lease-TTL gotcha below.
- `docs/dynamic-openstack-credentials.md` — the OpenBao/ESO dynamic-credential walkthrough (own numbered steps 1-4), required by README step 7, not optional. Split into its own doc so the README stays a straight read-through.
- `docs/least-privilege-openstack-credentials.md` — design doc for a *different* secret0 answer than `openbao/`: a narrowly-scoped static "root" credential (one new Keystone role, `cluster-provisioner`, plus `policy.yaml` overrides on keystone/neutron/nova) instead of OpenBao's dynamic app-credentials. Covers what ORC can do declaratively (`Project`/`User`/`RoleAssignment`/`ApplicationCredential`) vs. what needs scripting (Neutron RBAC-share, quota — no ORC CRD exists for either), several hard Keystone limits found by testing live (cross-user `ApplicationCredential` creation is unconditionally blocked in Keystone's own code, not policy-configurable), and validation steps run against the real DevStack. Not wired into any cluster in this repo yet — reference design.
- `provisioning/` — the scripted half of that design: template Jobs (`<cluster>` placeholders, not applied as-is) for the two actions ORC can't do declaratively (Neutron RBAC-share, quota) plus the Secret-bridging Jobs the design needs (`01-generate-secrets-job.yaml` pre-creates the Secrets neither ORC nor these Jobs can `create` themselves; `04-materialize-clouds-job.yaml` combines `ApplicationCredential.status.id` with the raw secret value into a real `clouds.yaml`). Ordered via ArgoCD `hook`/`sync-wave` annotations, documented in `provisioning/README.md`.

## End-to-end flow at a glance

DevStack on KVM (separate repo) → minikube management cluster on the `devstack_net` KVM network → `clusterctl init --infrastructure openstack` (preceded by `CLUSTER_TOPOLOGY=true` and applying the ORC `install.yaml --server-side`) → install the Talos providers (CABPT/CACPPT, via explicit provider URLs — `clusterctl`'s registry still points at the renamed `talos-systems` org) → install `talosctl` → set up OpenBao + External Secrets Operator so OpenStack credentials are minted on demand (`docs/dynamic-openstack-credentials.md` steps 1-3) → fetch a Talos node image from Image Factory and upload it → apply `talos-devstack01/` (roleset Job → `VaultDynamicSecret`/`ExternalSecret` → `OpenStackClusterIdentity` → `Cluster`+`TalosControlPlane`+`MachineDeployment`) → `clusterctl describe cluster` / `clusterctl get kubeconfig` → pull the CACPPT-generated `talosconfig` Secret and drive the cluster with `talosctl`. Steady state today is "a Talos control plane + worker exist and are reachable" — no CNI/CCM/GitOps layer on top yet (see "Parked" above).

## Repo-specific conventions worth knowing

- Cluster name is `talos-devstack01` throughout (namespace, roleset name, `OpenStackClusterIdentity`, `Cluster`/`TalosControlPlane`/`MachineDeployment` names all match). If renamed, update every name in `talos-devstack01/*.yaml` together — nothing is templated, it's all literal.
- The Talos provider install works around `clusterctl`'s stale `talos-systems` GitHub org via explicit provider URLs in `~/.cluster-api/clusterctl.yaml` — the URL shape is `.../releases/<version>/<file>`, not GitHub's literal `.../releases/download/<tag>/<file>` (`clusterctl` inserts `download` itself).
- `talosctl` version should track the Talos node image version (`v1.13.8` as of this writing, from the Image Factory URL) — some client/node skew is tolerated, but keep them close.
- CABPT/CACPPT are unmaintained upstream (Sidero Labs points to Omni instead); pinned to their last v1beta1-only stable releases (CABPT v0.6.12, CACPPT v0.5.13). Works against this repo's CAPI v1.13.0/v1beta2 management cluster the same way CAPO (also v1beta1-primary) does — via CAPI's `apiGroup`-only `ContractVersionedObjectReference`.
- **OpenBao lease TTL vs. Octavia LB wait**: `apiServerLoadBalancer.enabled: true` on `talos-devstack01/04-cluster.yaml`'s `OpenStackCluster` means `capo-controller` holds one authenticated client for the whole reconcile, including Octavia's LB active-wait poll (~2min observed on this DevStack). `openbao/setup.sh`'s lease TTL is 300s specifically to outlast that poll — a shorter TTL risks Vault revoking the credential mid-poll (confusing 404 `Could not find Application Credential` instead of a clean retry). If your Octavia is slower, raise it further.
- `clouds.yaml.example` / `.gitignore`'s `clouds.yaml` entry are a convenience for running `openstack` CLI locally — not part of the credential chain CAPO actually uses (that's OpenBao → ESO → `OpenStackClusterIdentity`, entirely in-cluster).
- **CAPI v1beta2 + CAPO v1beta1**: CAPI core refs use `apiGroup:` (`ContractVersionedObjectReference`); the CAPO-pointing refs on `Cluster.spec.infrastructureRef`, `MachineDeployment.spec.template.spec.infrastructureRef`, and `TalosControlPlane`'s `infrastructureTemplate` also resolve against whichever version CAPO's CRD currently serves (v1beta1). Don't re-add `apiVersion:` to any `apiGroup:`-style ref in a v1beta2 kind.

## Editing guidance

There is no in-repo validation. Changes to `talos-devstack01/*.yaml` or `openbao/setup.sh` only take effect by re-applying/re-running them against a live DevStack + minikube setup. When adjusting these files, cite the README step number rather than duplicating the command blocks.
